# 性能优化分析

- 范围：训练循环的吞吐与显存。只讨论不改变论文算法的优化；会改变算法的项单列在第5节，需要消融后才能采用。
- 代码版本：提交35b7e23加工作区修复（参考朝向四元数存储、评估按段长分批、梯度有限性每迭代检查一次、多卡批量口径选项）。
- 测量：`scripts/profile_train.py`，在Rara（RTX 4070 Ti SUPER 16 GB，Windows，`torch.compile`关闭，bf16）上用LAFAN1 40段测得。
  结论中凡标“估计”的数字均未实测。H100与Linux（开启`torch.compile`）的数字需要用同一脚本在服务器上复测。
- 相关：[training_pipeline.md](training_pipeline.md)第10节给出每次迭代的计算量。

## 1. 测量方法

`scripts/profile_train.py`原样运行训练脚本，不改训练代码：策略优化器每次迭代恰好step一次，
用全局优化器钩子推进`torch.profiler`的调度，跳过前`--wait`次策略更新，热身后记录`--active`次完整迭代。
输出每次迭代的GPU忙碌时间、按类别汇总的kernel数与耗时、主机侧的kernel发射与同步次数，以及峰值显存。

```bash
uv run --frozen python scripts/profile_train.py --report logs/profile.json --wait 15 -- --num_envs 512 --buffer_steps 100 --wm_batch 512 --pi_batch 512 --iterations 50 --wm_only_iters 10 --warmup_steps 16 --log_dir logs/prof_run
```

## 2. 测量结果

### 2.1 总览

| 配置（环境数 = 世界模型批 = 推演条数） | 每次迭代 | GPU忙碌 | kernel数 | 其中短于10 µs | 主机同步 | 峰值显存（已分配） |
| --- | --- | --- | --- | --- | --- | --- |
| 512 | 0.78 s（剖析中） | 248 ms（32%） | 68,187 | 65,176 | 86次，阻塞16 ms | 3.2 GiB |
| 2048 | 1.48 s（剖析中）；不剖析约1.0 s | 638 ms | 69,687 | 60,041 | 49次，阻塞78 ms | 7.9 GiB |
| 4096（论文单卡口径） | 无法完成 | — | — | — | — | 超出16 GB，WDDM换出到系统内存后几乎停滞 |

512环境下按阶段计时（`SM_PROFILE=1`，此前A/B测试）：采样2步约40 ms，世界模型10次更新230–290 ms，策略与critic 225–263 ms。

### 2.2 kernel类别（2048配置，每次迭代）

| 类别 | GPU耗时 | kernel数 | 平均每个 |
| --- | --- | --- | --- |
| 矩阵乘（GEMM） | 354 ms | 6,789 | 52 µs |
| 逐元素与其他 | 122 ms | 34,370 | 3.5 µs |
| 拷贝与类型转换 | 102 ms | 25,024 | 4.1 µs |
| LayerNorm | 36 ms | 912 | 39 µs |
| 归约 | 10 ms | 1,553 | 6.7 µs |
| 索引与gather | 8 ms | 769 | 10 µs |

主机侧：`cudaLaunchKernel`每次迭代64,389次，CPU耗时169 ms（约2.6 µs一次），尚不含PyTorch算子分派的Python与C++开销。
其中bf16权重转换kernel 2,792个、GPU 34 ms。

### 2.3 读数

1. **瓶颈是kernel发射，不是算力。** kernel数约6.8–7.0万，几乎不随批量变化；批量从512增到2048，GPU耗时增加2.6倍，
   每次迭代时间只增加约0.3倍。512配置下GPU有68%的时间在等CPU。
2. **真正的计算集中在GEMM。** 2048配置下GEMM占GPU时间的55%，平均52 µs一个，是有效负载；
   其余约6万个kernel平均不到4 µs，大多是旋转、FK、观测、归一化等小张量运算的逐元素kernel。
3. **对H100目标的含义。** 论文单卡约每次迭代0.11 s（32万次约10 h）。仅按每次2.6 µs计，
   发射6.4万个kernel就需要约0.17 s的CPU时间，已经超过目标。所以在H100上，kernel融合（`torch.compile`或CUDA graph）
   是达到论文耗时的必要条件，不是锦上添花（估计）。README记录的Linux GPU验证是在`--compile off`下做的，编译路径尚未验证。
4. **显存随推演条数近似线性增长。** 3.2 GiB（512）到7.9 GiB（2048），外推到4096约15 GiB以上（估计），
   主体是BPTT保存的32步激活。16 GB卡跑不了论文单卡配置；H100 80 GB的余量需要实测。

## 3. 优化项

按“收益 / 工作量 / 风险”排序。收益除特别注明外均为估计。

### P0：kernel融合（决定能否达到论文耗时）

**3.1 在Linux上启用并验证`torch.compile`。**
- 现状：`--compile auto`在Linux上默认开启，编译世界模型展开、单步推演、奖励与软终止、critic特征和世界模型误差五段；
  但这条路径没有经过实测，参考朝向改为`RotationView`后也未在编译下验证。
- 做法：在服务器上分别用`--compile on`和`--compile off`跑`scripts/profile_train.py`，对比kernel数、GPU忙碌率和每次迭代时间；
  检查编译期间的图中断（`TORCH_LOGS=graph_breaks`）与重编译次数。
- 收益：逐元素与拷贝类kernel（约6万个）是融合的主要对象，预期kernel数下降一个数量级（估计）。
- 风险：首次编译耗时数分钟；动态形状（例如多卡余数导致的不同本地批量）可能触发重编译。

**3.2 对固定形状的阶段使用CUDA graph。**
- 世界模型拟合（10次 × 8步展开、反传、裁剪、Adam）和想象推演加BPTT的形状每次迭代都相同，适合整段捕获。
- 前提：捕获区内不能有主机同步（见3.5），优化器要用`capturable=True`，随机数需走CUDA graph安全的生成器。
- Windows没有Triton，`torch.compile`的Inductor后端不可用，但`torch.compile(backend="cudagraphs")`或手动`torch.cuda.CUDAGraph`不依赖Triton，
  可以作为Windows开发卡的加速路径（未验证）。
- 风险：实现量中等；捕获后调试困难，需要保留关闭开关。
- **已实施**（`--cuda_graph`，见第6节）：手动`torch.cuda.CUDAGraph`，Windows可用。

### P1：低风险、改动小

**3.3 把bf16自动混合精度的作用域提到每次更新外层。**
- 现状：`run_mlp`每次调用都新开一个`torch.autocast`上下文。autocast的权重转换缓存在最外层上下文退出时清空，
  所以同一组权重在一次策略更新的32步展开里被反复转换成bf16。实测每次迭代2,792个bf16转换kernel、34 ms GPU。
- 做法：在世界模型更新、策略更新和critic更新的外层各开一次autocast，`run_mlp`内部的上下文变成嵌套、复用缓存。
- 收益：预计减少约2,500个kernel和30 ms GPU时间。
- **实测后不采用**（第6节）：前向输出逐位不变，但梯度不是。共享同一份bf16权重副本后，32步展开里各步的梯度先在bf16里累加、再转回fp32；
  原来每步各自转回fp32再相加。相对fp32参考的梯度误差中位数从4.5e-3升到1.6e-2，所以“数值完全不变”的判断不成立。

**3.4 三个优化器改用融合版Adam（`fused=True`）。**
- 现状：每次迭代31次Adam step（世界模型10次、策略1次、critic 20次），默认的foreach实现每次仍有多段kernel。
- 收益：kernel数小幅下降；critic的20次小网络更新受益最明显。数值与非融合版在浮点误差内一致。
- **已实施**（`--fused_adam`，第6节）：Rara上几乎无提速。注意`load_state_dict`会用检查点里的fused标志覆盖当前设置，恢复训练后须重新设回。

**3.5 去掉训练路径上的主机同步。** 实测每次迭代49–86次，来源：

| 来源 | 每次迭代次数 | 做法 |
| --- | --- | --- |
| `RunningNorm.update`里的`self.count >= self.max_count`判断 | 采样每步4次 × 2.5步，加critic 1次 | 改为在GPU上按`count < max_count`计算权重，冻结后权重为0，不在主机上分支 |
| `TrackingSim.step`里的`done.nonzero()`与`len(ids)` | 每个仿真步1次 | mjlab的`Simulation.reset`本身支持掩码；可改为整批按掩码重置，只在需要统计时同步 |
| `sample_valid_starts`的拒绝采样循环 | 每次策略更新至少1次 | 维护缓冲中“后面还有H帧参考”的有效掩码，直接按掩码抽样 |
| 策略梯度的`torch.isfinite(gn)`判断 | 1次 | 保留，或改为在GPU上把非有限梯度置零后照常step |
| 多卡`average_gradients`里的`.tolist()` | 每次梯度平均1次，共31次 | 参数是否被使用在一次运行中固定，首次计算后缓存 |

收益：单看CPU阻塞时间只有16–78 ms，但它们也是CUDA graph捕获的前提（3.2）。

- **已实施的部分**（第6节）：`RunningNorm.update`改为GPU上判断冻结。其余来源未改：采样每步约27次同步来自mjlab按`env_ids`写状态的内部实现，
  改成整批掩码重置会改变随机数消耗顺序；`done.nonzero()`和拒绝采样各约1–2.5次，且不在CUDA graph捕获范围内。

**3.6 前向运动学按树深度批量计算。**
- 现状：`G1Kinematics.forward`按30个刚体逐个串行计算，每个刚体约十个小kernel；奖励、critic特征和参考库构建都会调用。
- 做法：G1运动树的最大深度约11层（腿约7层），同一深度的刚体彼此独立，可以合并为一次批量矩阵运算，
  kernel数从“刚体数 × 每体算子数”降为“深度 × 每层算子数”。
- 收益：FK相关kernel约减为三分之一（估计）；开启`torch.compile`后收益会被融合覆盖，所以优先级低于3.1。

### P2：先在H100上测量，再决定

**3.7 仿真与训练重叠。**
- 想法：仿真在单独的CUDA流上采集下一次迭代的数据，同时在当前缓冲上做世界模型和策略更新，数据新鲜度滞后一次迭代。
- 依据：按论文图5(a)的吞吐读数粗估，H100上仿真可能占总时间的三到九成（未实测）；但在Rara的512环境下采样只占约7%。
  是否值得做取决于H100上的实测比例。
- 风险：改变了“先采样再更新”的顺序，属于算法层面的细微变化（Dyna允许，但需要消融）；实现复杂度高。

**3.8 显存：BPTT激活与参考库。**
- 激活：按每个想象步做梯度检查点，可以用约三成额外计算换取大部分激活显存（估计），使论文单卡配置或H=128能在较小显存的卡上运行。
  H100 80 GB上H=32是否需要，取决于实测峰值。
- 参考库：当前每帧1,052字节，本索引全量38.85 GiB。若身体位姿和速度改为奖励计算时在线FK，可去掉每帧14 × 13个浮点数，
  降到约每帧324字节、约12 GiB（估计）；代价是每次奖励计算多一次参考FK。

**3.9 多卡通信。**
- 现状：每次更新把全部梯度拼成一个大张量同步，不与反向传播重叠；世界模型每次约9M参数，每次迭代10次。
- 做法：按桶异步all-reduce并与反向重叠（DDP Reducer的做法），或至少去掉3.5中的`.tolist()`同步。
- 收益只在多卡时体现；NVLink互联的8卡H100上可能很小，需实测。

**3.10 评估。**
- 已完成：默认每批4096个环境、按段长从长到短分批。
- 可选：训练与评估各占一张卡并发，评估不占训练时间。

## 4. 建议顺序与验证方法

1. **服务器基线**：在H100上用`scripts/profile_train.py`分别测`--compile off`与`--compile on`，配置用论文单卡口径
   （`--num_envs 4096 --wm_batch 2048 --pi_batch 4096`，默认`--buffer_steps 1000`）。这一步决定后续各项的优先级。
2. **低风险项**：3.3、3.4、3.5的前三项。每项单独提交，提交前后用同一配置各测两轮，对比每次迭代时间和kernel数；
   训练曲线（`wm_err8`、想象存活率、仿真回报）在固定种子下应基本一致。
3. **CUDA graph**（3.2）：在3.5完成后进行。
4. **视实测决定**：3.7、3.8、3.9。

每一项都要保留开关或可回退的提交，并在README记录实测结果，不把估计写成结论。

## 5. 不建议做的优化（会改变算法）

以下做法可能更快，但会偏离论文表A.5，复现阶段不采用，除非作为消融单独报告：

- 减少每次迭代的世界模型批数（10批）或窗口长度（k=8）；
- 缩小世界模型或策略网络（2048宽MLP）；
- 提高更新数据比、缩短想象长度H；
- 用fp16或fp8替代bf16做推演；
- 用多步动作或降低控制频率减少仿真步数。

## 6. 实施记录（2026-10-26，分支`perf/systematic-opt`）

范围：只做数值不变或只差浮点舍入的提速，每项单独提交并保留开关。全部在Rara（RTX 4070 Ti SUPER 16 GB，Windows，`torch.compile`不可用，bf16）上测得。

**测量方法**
- 速度：2048环境（`--wm_batch 2048 --pi_batch 2048 --buffer_steps 100`），80次迭代，取第30次之后的平均it/s；
  main与本分支交替各跑3次，抵消桌面负载造成的波动。
- 数值：单次更新逐位比较；训练层面用固定种子、512环境、150次迭代，与main两次运行之间的波动比较
  （同种子的两次main运行本身就不完全一致，第150次迭代wm 0.324对0.336）。

| 项 | 开关（默认） | 数值 | 速度（2048环境） | 结论 |
| --- | --- | --- | --- | --- |
| 3.3 autocast作用域上提 | — | 前向逐位不变；梯度相对fp32误差中位数4.5e-3 → 1.6e-2 | 未测 | 不采用 |
| 3.4 fused Adam | `--fused_adam on` | 50步后参数差约为更新量的1e-5 | 0.936 → 0.933 s/iter（剖析） | 采用，提速可忽略 |
| 3.5 `RunningNorm`去同步 | 无开关（逐位不变） | 跨冻结点逐位一致 | 与3.4合计 0.922 → 0.912 s/iter，在波动内 | 采用；同步86 → 75次/迭代 |
| 3.2 CUDA graph | `--cuda_graph auto` | 图重放与直接调用逐位一致（含随机数）；相对main只差浮点舍入 | 0.911 → 0.833 s/iter（−9%）；512环境1.87 → 2.92 it/s（+56%） | 采用 |

**CUDA graph的实现要点**
- 捕获两段：世界模型的一次更新（展开、损失、反传、裁剪、Adam，每次迭代重放10次），策略的想象推演加BPTT与Adam。
  回放缓冲采样、观测历史、critic更新仍直接执行。前3次调用直接执行（真实更新，同时预热cuBLAS与显存分配器），第4次捕获并重放。
- `auto`只在单进程、CUDA、未开`torch.compile`、未设`SM_PROFILE`时启用；`torch.compile`加图的组合当时未验证，A100上的结果见7.2节。
- 多卡需显式`--cuda_graph on`：图内的梯度all-reduce改用固定的全局样本数（`average_gradients(..., total_count=...)`），
  省去“哪些参数有梯度”的主机往返；被捕获的两步里所有参数每次都有梯度，这条路径与通用路径逐位一致（CPU/gloo两进程单测）。
  捕获时用`capture_error_mode="thread_local"`，因为NCCL的watchdog线程会在捕获期间查询CUDA事件。
  Rara只有一张卡，当时未实测NCCL多卡下的捕获（后在A100双卡上逐位验证，见第7节）；`scripts/check_cuda_graph.py`可在目标机器上用torchrun逐rank检查图重放与直接执行是否逐位一致。
- 世界模型与策略的Adam改为`capturable=True`，学习率改为设备上的张量，每次迭代原地写入调度值。
- `torch.cumprod`的反向会在主机上判断输入里是否有0，无法捕获；启用图时存活权重改为逐步连乘，前向与cumprod逐位一致，反向只差浮点舍入。
- 图里不能在主机上分支，策略梯度非有限时也照常step；这种情况本迭代末仍会报错退出，不会记录或保存。
- 显存：已分配峰值7.74 → 7.79 GiB，保留峰值9.12 → 11.06 GiB（两张图各自的私有显存池）。
- `scripts/profile_train.py`靠策略优化器step的Python钩子推进剖析调度，图重放不触发钩子，剖析时需加`--cuda_graph off`（设`SM_PROFILE=1`时`auto`本来就关闭）。

**未做的项**
- 3.6 FK按树深度批量：策略推演里的FK已被CUDA graph覆盖，剩余调用在采样和critic特征里，次数少；未实施。
- 3.1 `torch.compile`、3.7–3.9：需要Linux或H100实测，未在本机进行。A100上compile的实测见7.2节。

## 7. A100实测与后续记录（2026-10-26至27，分支`perf/critic-graph`、`perf/env-reward-graph`，均未合并）

**环境与口径**
- 服务器A100（Linux，Python 3.12，torch 2.14.1+cu130，`torch.compile`可用），每个实验单卡（双卡检查除外）。
- 论文单卡口径：4096环境，世界模型10批×2048窗口，策略批4096，`--buffer_steps 1000 --amp bf16 --fused_adam on --seed 0`；
  数据为过滤后BONES-SEED的前5000段（`--motion_limit 5000`）。
- 速度取第30次迭代之后it/s均值的倒数。“配对”指同一批次、在不同卡上同时运行的对照组；不同批次之间的绝对值随服务器负载浮动几个百分点，只比较同批数字。
- 逐位检查：`scripts/check_cuda_graph.py`，单卡与`torchrun --nproc-per-node=2 ... --batch_scope per_gpu`（NCCL）各跑一次，运行时`torch.compile`为on。

### 7.1 世界模型段的耗时构成

`SM_PROFILE=1`、`--compile on`、不开图，只改世界模型批量：

| 世界模型批量 | 世界模型段（10次更新） | 采样（2步） | 策略+critic |
| --- | --- | --- | --- |
| 256 | 277 ms | 120 ms | 443 ms |
| 2048（论文） | 279 ms | 114 ms | 432 ms |
| 4096 | 323 ms | 123 ms | 447 ms |

批量从256增到2048只多2 ms，从2048增到4096多44 ms。据此推算2048个窗口的实际计算约45 ms，其余约235 ms与批量无关，
是kernel发射、Python调度和10次优化器更新的开销（估计）。“论文每次迭代只做1次世界模型更新、本实现多做了10倍”的猜测不成立：表A.5写的就是10批×2048。

### 7.2 `torch.compile`与CUDA graph的组合

| `--compile` | `--cuda_graph` | 每次迭代 | 相对全关 |
| --- | --- | --- | --- |
| off | off | 1.457 s | 1.0× |
| off | on | 0.716 s | 2.0× |
| on | off | 0.869 s | 1.7× |
| on | on | 0.512 s | 2.8× |

- 四组跑到第100次迭代时损失与回报处于同一水平；compile加图时图重放与直接执行逐位一致（单卡与双卡NCCL）。
- 两者可以叠加。`--cuda_graph auto`在开compile时不启用图，Linux上要显式加`--compile on --cuda_graph on`。
- 按0.512 s/iter计，32万次迭代单卡约46 h。论文只给出“单卡3 h回报超过SONIC”，没有写3 h对应的迭代数，两者不能直接按小时比较。

### 7.3 critic更新放进CUDA graph（`perf/critic-graph`，提交c29e9f6）

- 开关：`--cuda_graph_critic on|off`（默认on，仅在CUDA graph启用时生效）。
- 内容：GAE目标与5轮×4小批的梯度步整体捕获，critic的Adam改为capturable；多卡下每个小批的全局样本数在启动时算好，
  走固定计数的梯度all-reduce；`global_moments`改为在设备上填样本数，捕获期间跳过需要主机的样本数检查。
- 逐位：Rara单卡、A100单卡、A100双卡NCCL下，世界模型、策略、critic三步的输出、参数与缓冲都逐位一致。
- 速度（配对各2组）：关0.4616 / 0.4636 s → 开0.4582 / 0.4584 s，约快0.9%。
- 读数：不开图时分段计时里critic约100 ms，图化收益远小于此。分段计时前后都有同步，而图化只省CPU发射、不省GPU计算，所以分段数字不能直接当作可省的时间。

### 7.5 采样一步的拆解与主机同步

单独运行时（训练30次迭代后测，每步约108个环境重置）：

| 部分（前后加同步单独计时） | 耗时 |
| --- | --- |
| `collect(1)`整步 | 52.7 ms（另一批次34.7–43.2 ms，随负载浮动） |
| 策略侧（观测、目标、归一化、策略前向） | 7.1 ms |
| 后处理（`buffer.add`、世界模型归一化） | 5.5 ms |
| 物理4个子步 | 16.7 ms（只算`sim.step`为14.2 ms，约28.8万env-step/s） |
| `env.reset(k)` | 3.3 ms，k=8到512不变 |

每步GPU忙碌约18–19 ms，主机同步13.1次。来源：

- 12次是同一种写法：用CUDA下标张量写Python标量，`x[ids] = 0.0`。
  其中mjlab `EntityData.clear_state`里7次（7个执行器目标清零），mjlab `Simulation.reset`里`_reset_mask[env_ids] = True`1次，
  `TrackingSim.reset`里4次（`ep_step`、`a_prev`、`ep_disc_ret`、`ep_ret`清零）。
  在torch 2.14.1上，这种写法每次同步一次；`index_fill_`或写零张量不同步，结果相同。写入值本身是张量的（如`self.f[env_ids] = frames`）不同步。
- 1次是`done.nonzero()`：每步重置的环境数不固定，这次同步省不掉。

**去掉那12次同步的实测**：只在测量工具里于运行时把这12处改成`index_fill_`，仓库代码不变。

- 每步同步从13.1次降到1.0次。
- 重置1、37、300个环境三种情况，比较23个张量（其中15个被重置改写），逐位一致。
- `collect(1)`同一进程交替8轮，中位数34.78 → 34.64 ms，约快0.4%，在波动内。**未采用。**
- 几乎没有收益是因为这12次都在`nonzero`之后：那时GPU队列已经空了，每次同步只需要等几个很小的kernel。

**不加同步的主机时间线**：在关键位置记录主机时间戳，不额外同步。这一进程里每步43.2 ms，看比例：

| 阶段 | 主机耗时 | GPU |
| --- | --- | --- |
| 策略侧（发射） | 7.1 ms | 基本空闲 |
| `env.step`到第一个物理子步发射 | 1.4 ms | 基本空闲 |
| 发射4个物理子步 | 1.7 ms | 开始跑物理 |
| 发射奖励图、算done，在`done.nonzero()`等GPU | 21.5 ms | 物理、奖励（CPU空等） |
| 重置（含那12次同步） | 5.5 ms | 基本空闲 |
| 后处理（发射） | 5.9 ms | 基本空闲 |

CPU干活的约21 ms里GPU基本空闲，GPU跑物理和奖励的约21 ms里CPU在空等，两者没有重叠。
剖析器统计的主机阻塞在`cudaStreamSynchronize`里约15 ms/步，与此一致。
采样每次迭代2.5步（`--utd 0.4`），约占整次迭代的五分之一。
